# 3層監査ループと完成基準

「作った」と「完成した」を区別するための監査手順。自己申告での完成宣言を禁止し、
**証拠(チェックリスト結果+レンダリング画像)**で完了判定する。

## 運用ルール

- 監査は L1(構造)→ L2(仕様)→ L3(視覚)の順。前の層のBlockerを残したまま次へ進まない
- 指摘は3段階に分類:
  - **Blocker**: メッセージ不成立、はみ出し、データ誤り、ゾーン違反 → 必ず修正
  - **Major**: 整列ズレ、仕様外の色/pt、強調過多、凡例欠落 → 必ず修正
  - **Minor**: 語尾の不統一、より良い言い回し等 → 時間内で修正、残れば報告
- ループは**最大3周**。3周後に残る項目は「既知の制約」として納品時に明記する
  (黙って納品しない)
- 修正は必ず**設計書→コード→再レンダリング**の順で反映(pptxを直接いじって設計書と
  乖離させない)

## L1: 構造監査(実装前、設計書に対して)

- [ ] メッセージラインは主張を含む完全な文か(体言止め・ラベル化していないか)
- [ ] メッセージラインだけの通し読みで論旨が通るか(ストーリーの飛び・重複がないか)
- [ ] 各スライドの図解パターンは決定木の出力と一致するか。記載は3通りのいずれかか:
    ①R対応パターン(P-1〜P-4/P-15〜P-19)はR番号+理由 ②決定木の直接出力
    「R5型」「R6型」はその型名+理由 ③P-5〜P-14は「R対応なし・P-x準拠」+理由
    ④再掲は「P-19+再掲オーバーレイ(ベース: Slide N)」
- [ ] 図はメッセージを「見れば分かる」形で証明しているか(証明チェック)
- [ ] 要素数がパターンの上限内か(過密チェック)。超過スライドは分割済みか
- [ ] **密度検算が済んでいるか**(density-composition.md §6)。本編の分析スライドで
    「薄すぎ警報」(文字量300字未満/情報単位10未満)に該当するものが残っていないか
- [ ] 複合構成(C-1〜C-5)の採否が全スライドで記録されているか
- [ ] 定量メッセージのスライドに比例描画チャートが計画されているか(数字入りの箱の
    羅列をチャートと呼んでいないか)
- [ ] データの切り口は1スライド1つか。切り口候補の集計→採否の記録があるか
- [ ] すべての数値に出所と時点があるか。推計は「XX推計」と区別されているか
- [ ] 構成比の合計・内訳の和は検算済みか
- [ ] 読者(Phase 0で確認)に対して粒度は適切か(経営層に実務詳細を見せていないか)

## L2: 仕様監査(実装後、**監査スクリプトの実行が必須**)

チェックリストを「読んで確認」することを禁止する。以下のアルゴリズムを実装した
監査スクリプトを**実際に実行**し、その出力ログ(PASS/違反リスト)を取得すること。
ログのない完了報告は虚偽報告とみなす。python-pptxが使える環境ではpptxを開いて走査、
使えない環境ではpptxをzip展開しXML(a:off/a:ext等)を解析する。

```
for each slide, each shape:
  1) bounds:   x≥0, y≥0, x+w≤33.867cm, y+h≤19.05cm。テキストshapeは y+h≤17.0
               (フッター類 y≥17.0 は除外)                     → 違反=Blocker
  2) palette:  塗り・線・文字色が design-system.md パレットのhex集合に含まれる
                                                              → 違反=Major
  3) font:     フォント名が規定の1書体(EastAsian含む)、サイズが8〜34ptの規定値
                                                              → 違反=Major
  4) text-fit: 文字数から必要寸法を計算し shape 寸法と比較:
               1行字数 = floor((w−0.4) / (pt×0.0353))
               必要h   = ceil(字数/1行字数) × pt×0.0353×1.25 + 0.2
               必要h > h なら溢れ                              → 違反=Blocker
  5) overlap:  テキストを持つshape同士のAABB交差面積が小さい方の面積の10%超
               → 違反=Blocker。**重なり許可リスト**(検査から除外するペア): ①背景帯・
               塗り領域(チェブロン/バナー/コールアウト帯/バー)の上に置くラベル
               ②丸数字・ローマ数字バッジと母体shape ③リスクマーカーと母体shape
               (いずれも重なりが意図されたブループリント部品。それ以外は全て検査対象)
  5b) pitch:   縦に隣接するテキストshape列で 次shapeのy − 前shapeのy < 前shapeのh
               となる積み上げ(=構造的重なりの署名)          → 違反=Blocker
  6) blueprint: ブループリント表の固定座標shape(共通フレームF1〜F7、各Rの固定要素)
               が表の座標±0.05cmに存在する                     → 違反=Major
  7) chart:    バー群について h_i/h_j と v_i/v_j の乖離が5%以内(比例描画の実在)
               データ辞書がコードに存在する                     → 違反=Blocker
  8) arrows:   フロー図(P-1/P-18等)のコネクタ・矢印それぞれについて、中点から
               1.0cm以内にラベルテキストが存在する(「何が流れるか」の明記)
                                                              → 違反=Major
出力: スライド別の違反リスト(種別・shape・座標・内容先頭15字)と総括 PASS/FAIL
```

上記に加えて確認する項目:

- [ ] 全色が design-system.md のパレットhexと一致(想定外RGBの検出)
- [ ] 全フォントサイズが仕様表の範囲内、最小8pt以上
- [ ] フォント名が全runで統一されているか(East Asian含む)
- [ ] 図形・テキストがボディゾーン(y: 4.2–16.9cm)からはみ出していないか。
    スライド外(負座標・33.87cm超)の要素がないか
- [ ] 共通部品(メッセージライン・脚注・出所・ページ番号)の座標が全スライドで同一か
- [ ] 同種要素の整列(x座標・幅・高さの一致、等間隔)が保たれているか
- [ ] テキスト量の事前検算(design-system.md §4)に対する超過がないか
- [ ] **60字超のテキストボックスの検出**(メッセージライン・リード文・示唆カラム・
    コールアウト帯を除く)。検出されたら箇条書き分解・表化・図解化で解体
- [ ] **比例描画の実在検証**: 定量スライドについて、チャートを構成する矩形の高さ/幅が
    データ辞書 `values` の値に比例しているかを計算で照合(値だけ書いた飾り矩形の検出)
- [ ] スライド別の総文字数・shape数を集計し、密度基準(density-composition.md §1)との
    乖離一覧を作る(全スライド平均が薄い場合はL1へ差し戻し)

検査スクリプトの出力(違反リスト)を監査記録に残す。

## L3: 視覚監査(レンダリング画像の目視)

**レンダリングせずに完成宣言することを禁止する。**

手順:
1. pptx → PDF → PNG に変換して各スライドを画像化する
   - claude.ai / Linux: `soffice --headless --convert-to pdf out.pptx` →
     `pdftoppm -png -r 100 out.pdf slide`
   - Windowsローカル: PowerPoint COM で `SaveAs`(PDF)後に変換、または
     エクスポート機能。いずれも不可の環境では、その旨を報告し L2 の強化
     (座標の全数検算)で代替したことを明記する
2. 各スライド画像を1枚ずつ開いて以下を目視確認:

- [ ] 3秒テスト: 画像を見て3秒でメッセージが掴めるか(図の主役がどこか一目で分かるか)
- [ ] テキストの折返し・欠け・重なりがないか(自動折返しによる不自然な改行含む)
- [ ] 余白の質(ゾーン間に規則的な余白があるか、片側に偏った「何もない面」がないか。
    ※密度基準 density-composition.md §1 が優先 — 高密度スライドの余白が少ないこと自体は
    指摘対象にしない)
- [ ] 強調が1箇所に絞れているか。逆に強調ゼロで平板になっていないか
- [ ] 矢印・線が要素に正しく接続しているか(浮いた矢印、ズレた接続)
- [ ] 白背景・単色アイコン・影なしが守られているか(意図しない既定スタイル混入)
- [ ] 隣接スライドと共通部品の位置が揃って見えるか(パラパラめくりでズレが見えないか)
- [ ] 全角/半角、数字の桁区切り、「%」「億円」等の単位表記が資料内で統一されているか
- [ ] **密度感テスト**: pattern-library.mdの基準スライド(R1〜R11)の記述と見比べて
    「明らかに要素が少ない・スカスカ」に見えないか。文章の壁(長文パラグラフの箱)が
    残っていないか
- [ ] チャートは「描かれて」いるか: バーの長さの差・セグメント割合が値どおりに見えるか、
    データラベルが全打ちされているか

3. 発見した指摘を Blocker/Major/Minor で記録 → 修正 → 再レンダリング → 再確認

## ユーザーフィードバックの受け方(差し戻しプロトコル)

1. フィードバックを「メッセージへの指摘 / 構成への指摘 / 見た目への指摘」に分類する
2. メッセージ・構成への指摘 → Phase 1〜2(設計書)に戻って直す。**見た目だけ直して
   ごまかさない**
3. 見た目への指摘 → 該当スライドの設計書のレイアウト割付を更新してから実装を直す
4. 修正後は、修正したスライドについて L2→L3 を再実行してから再納品する
5. 同じ箇所への指摘が2回来たら、局所修正をやめて設計書ごと作り直す(パターン選択の
   誤りを疑う)

## 完成宣言の条件(すべて満たして初めて「完成」と言う)

1. L1〜L3 のチェックリストが全項目済み(証拠: チェック結果と違反0の記録)
2. **L2監査スクリプトの実行ログ(PASS)が存在する**(実行せずにPASSと書くのは虚偽報告)
3. Blocker・Major 指摘が0(Minor の残存は列挙して報告)
4. 全スライドのレンダリング画像を目視済み(証拠: 画像ファイル一覧)
5. 納品物4点セット(pptx / スライド設計書 / L2監査ログ / 監査記録)が揃っている

## 品質の最終感覚チェック(監査を超えた審美)

チェックリストを全部通しても「BCGらしくない」場合、典型原因は:
- メッセージが弱い(事実の記述で主張がない)→ Phase 1 へ
- 図がメッセージの「挿絵」になっている(証明になっていない)→ パターン再選択
- **薄い(証拠の階層が2層で止まっている、チャートがない、示唆カラムがない)**
  → density-composition.md §2 の順で証拠を掘り増す。最頻の原因はこれ
- 詰め込みすぎ(1枚に2メッセージ)→ 分割
- 強弱がない(全要素が同じ視覚的重さ)→ 非強調をグレーへ落とす
- 言葉が長い(ボックス内が文章)→ 体言・短句化(※メッセージラインだけは文のまま)
