# 深さの審査(depth-review.md)― 別のモデルに採点させる依頼文

自分の示唆を自分で採点すると甘くなる。節目ごとに、**書いた本人とは別のモデル**に審査させる(thinking-moves.md の末尾)。
- この PC では Gemini(`~/dual-agent/bin/dg-batch`。審査は Hydrogen の high か xhigh、価値の芯に関わる審査は Argon)。
- agy が無い環境(クラウド・スマホ)では、新しい文脈のサブエージェント(`model: sonnet`)に同じ依頼文を渡す。サブエージェントも無ければ、
  時間を置かずに自分でやらず、依頼文の「審査の問い」を 1 つずつ紙に書くつもりで答え、`by` に「自己審査」と書く(検査は注意を出す)。
- 審査の結果は鵜呑みにしない。指摘 1 つごとに台帳で確かめ、正しいものだけ反映する。審査の誤りも記録に残す。
- 記録は `hypotheses.json` の `reviews` に書く: `{stage, by, date, findings(指摘の数), downgraded:[{id, from, to, why, action}], notes}`。
  `stage` は 構造・仮説・示唆 のどれか。`gate.py thesis` は、示唆の審査があること、段を下げられた示唆に対応(`action`)があることを検査する。

## 依頼文 1: 構造の審査(工程 2 の途中。型 1 の一文と事業の地図)

```
<作業フォルダ>/business_map.json と、hypotheses.json の plan.Q1(お金の流れの一文)を読む(Web は使わない)。
あなたは、この会社を知らない機関投資家。次の問いに、資料の原文を引用して答える。
1. 社名と製品名を伏せたら、この一文は同業他社にも当てはまるか。当てはまるなら、どの語が一般的すぎるか。
2. 値段が誰に・何に連動して決まるか、原価の何割が何に連動するか、値段への反映の時差が、数字で書いてあるか。無い項目を挙げる。
3. 利益がどの製品群・顧客にたまるかが、売上の構成比と利益の構成比の両方の数字で書いてあるか。
4. 成長を止めているもの(能力・人・認定・資金・需要)と、それが外れる日付が書いてあるか。
5. バリューチェーンの各段(原料 → 自社 → 顧客 → 最終需要)に、会社の外の開示の根拠があるか。会社の説明だけの段を挙げる。
出力: | 問い | 合否 | 原文の引用 | 足りないもの(調査項目として 1 行)|。最後に、この一文から読み手が「何を見れば利益が読めるか」を言えるか、1 行で。2,000 字以内。
```

## 依頼文 2: 仮説の審査(工程 2 の終わり。上位の驚きと対立仮説)

```
<作業フォルダ>/hypotheses.json の hypotheses(rivals を含む)と lenses.md を読む(Web は使わない)。
あなたは、この分析の結論に反対したい懐疑的なアナリスト。価値の芯に関わる仮説(value_link に「芯」)それぞれについて答える。
1. 対立仮説は 3 種類(構造の変化 / 一時・循環 / 業界共通・会計・計算の誤り)そろっているか。抜けている説明を 1 つ挙げる。
2. 「見分ける数字」は、本当に 1 つの仮説でしか起きないか。別の仮説でも同じ数字になる筋道があれば書く。
3. 対立仮説を消した証拠は、会社の一次情報か、会社の外の数字か、類推か。類推だけで消しているものを挙げる。
4. lenses.md の旗のうち、どの仮説にも示唆(insights の seed)にも使われておらず、結論を変えうるものはあるか。
5. 支持した仮説どうしで、言い分が食い違うものは無いか(例: 主因は数量と言いながら、別の所で値決めの力と言う)。
6. 期間や定義の違う数字を比べていないか。在庫の評価益・一過性の損益が混ざっていないか。
出力: | 仮説 id | 問い番号 | 指摘 | 決着させるデータ |。重要な順に最大 12 行。2,500 字以内。
```

## 依頼文 3: 示唆の審査(工程 6。示唆のカードと投資仮説)

```
<作業フォルダ>/hypotheses.json の insights・thesis・rebuttals と、valuation.json の sensitivities を読む(Web は使わない)。
深さの梯子: 1 開示の写し / 2 分解した / 3 因果を会社の外の数字で確かめた / 4 市場の前提との差分に 1 株あたりの値段と日付が付いた /
5 弱気の反論をデータで検証して残り、撤回の線が数字である。
あなたは、採点が厳しい運用責任者。示唆 1 つごとに、申告された段を 1 つ下げる理由を探す。
1. その示唆は、決算短信か決算説明資料を読めば書いてあることではないか(書いてあるなら段 1)。
2. outside は、会社の説明と独立に確かめられる証拠か(会社の外の開示・統計、または会社の説明を同じ会社の別の明細で突き合わせたもの)。
   会社の決算数値の時系列を集計・回帰しただけのものは分解であり、深さ 2 にとどめる。
   決算説明資料の文章の言い換えではないか。同業 1 社の例だけで「業界共通ではない」としていないか。
3. market_view は、株価・会社予想・会社の計画・過去の関係のどれから、どう計算した数字か。出所の無い「通説」ではないか。
4. value_per_share は valuation.json のどの数字と対応するか。対応が確かめられないものを挙げる。変数どうしの比較は、単位あたりではなく
   「ありうる振れ幅」で比べているか(単位を変えると順位が入れ替わらないか)。
5. falsifier は、決算で測れる数字と日付になっているか。tested_by の反論は、その示唆を本当に狙っているか。
6. thesis.one_line は、市場の前提・自分の見立て・差・時期・撤回の 5 つを含むか。thesis.kill は測れるか。
7. 反論の判定で、都合よく「逆」にしているものは無いか。
8. 示唆どうし、示唆と仮説の判定のあいだに、言い分の食い違いは無いか。
9. 将来の見立てが過去の延長になっていないか。日付のある段差・閾値・体制の転換が、上振れと下振れの両方で数えられているか。
出力: | 示唆 id | 申告の段 | 審査の段 | 下げた理由(問い番号)| 上げ直すのに要るもの |。全部の示唆を 1 行ずつ。
最後に、thesis への指摘(最大 3 つ)と、「この分析でいちばん弱い 1 点」。2,500 字以内。
```

## 依頼文 4: 構造の盲検(工程 2A の終わり。`structure.json`)

```
<作業フォルダ>/structure.json と structure_lenses.md を読む(Web は使わない。facts.json は数字の照合に使ってよい)。
あなたは、この業界で 10 年働いた人で、投資家ではない。書いた人は会社の資料を読んだだけの部外者だと疑っている。
1. 社名と製品名を伏せても、one_line と customer の区画だけで、同業他社と区別できるか。区別できないなら、どの文が一般的すぎるか。
2. customer の顧客の損益は、現場の感覚と合うか。合わない行と、正しそうな水準。会社の主張(claim)を測った結果(measured)は、測り方として公平か
   (母集団・期間・規模の違いを無視していないか)。
3. 業界の人なら当たり前なのに、industry・stakeholders・competitors に書かれていない事実を 3 つ挙げる(制度・資金の流れ・商習慣・失敗の理由)。
4. cases の 5 件は、平均の言い換えになっていないか。件ごとの差(why_different)は本当の理由か。
5. atom.flow の定常の規模とシェアは、流入・流出の定義(契約か稼働か、休止・切替の扱い、年度のずれ)をそろえて計算しているか。
6. competitors: 競合が何で儲けているか・安さの原資は、事実か推測か。推測の行を挙げる。
7. loop の「実証」のリンクは、相関を因果と読んでいないか。律速を内・外と判定した根拠は足りるか。
8. advantage・wallet・new_product_margin で、数字の並べ方が都合よくないか(期間・分母・増分の対応)。
9. mechanisms の上振れと下振れは同じ粒度か。確率と 1 株あたりの円に根拠があるか。抜けている最大の下振れは何か。
10. この structure.json を読んで、業界の人でも「それは知らなかった・その並べ方は無かった」と思う点はいくつあるか。番号を付けて挙げる(0 個なら 0 と書く)。
出力: | 区画 | 指摘 | 重さ(致命・要修正・軽微)| 決着させるデータ |。重要な順に最大 15 行。最後に「新しい発見の数」と「いちばん浅い区画」。3,000 字以内。
```

記録: `structure.json` の `review` に `{by, date, findings, new_to_insider(問い 10 の数), notes(指摘と対応)}`。致命・要修正の指摘は区画を直してから `gate.py structure`。
新しい発見が 3 個未満なら、`references/insight-patterns.md` の型で、まだ当てていないものを当て直す。

## 依頼文 5: 条件の審査(工程 4 の終わりと、工程 5 の 3 のあと。`conditions.json` の `deep`)

```
<作業フォルダ>/conditions.json(deep を含む)と structure.json を読む(Web は使わない)。評価の基準は references/condition-guide.md、深掘りの型は condition-deep-dive.md。
あなたは、採点が厳しい投資委員会の委員。条件 1 つごとに、評価を 1 段上か下に動かす理由を探す。
1. 決め手の問い(questions)は、その条件の本当の決め手か。抜けている決め手の問いを 1 つ挙げる(condition-deep-dive.md §2 と照らす)。
2. 答えの数字は structure.json・facts.json と合っているか。構造に無い事実を理由にしていないか。
3. test の比べる相手(benchmark)は公平か。この評価に要る水準(threshold)は、基準(condition-guide.md)と合っているか。
4. counter の「採らない理由」は数字で反論できているか。言い換えで退けていないか。
5. 既存の顧客の数字だけで、新規の場面・将来を語っていないか。今の数字で 5 年後・10 年後を語っていないか。
6. upgrade_if・downgrade_if は、その日に開示される数字で測れるか。
7. 条件どうしで言い分が食い違っていないか(例: 条件 12 は「従量で顧客の成長が乗る」、条件 1 は「単位あたりは横ばい」)。
出力: | 条件 | 申告 | 審査の評価 | 動かす理由(問い番号)| 足りないもの |。全条件を 1 行ずつ。最後に「採点がいちばん甘い条件」と「いちばん浅い条件」。2,500 字以内。
```

記録: `conditions.json` の `review` に `{by, date, moved:[{no, from, to, why, action}], notes}`。動かされた条件は、問いを足して答え直すか、評価を変える(`action` に書く)。

## 審査を受けたあと

- 段を下げられた示唆: 要るものを足して上げ直す(`action: "外の数字を追加: ○○"`)か、下げたままにする(`action: "段 3 に修正。資料では重み A"`)。
- 審査が何も指摘しなかったら、審査になっていない(依頼文に資料が渡っていないか、モデルが弱い)。モデルを上げてやり直す。
- 資料(bcg-slide-method)に進むのは、示唆の審査を反映し、`gate.py thesis` が PASS してから。
