# BCGスライド級スライド作成メソッド(bcg-slide-method)

分析文章を入力に、**「1スライド=1メッセージ、メッセージは図解が証明する」**構造の
BCG級スライドを作る手順書。ゴールは「読み手が各スライド3秒でメッセージを掴み、
30秒で根拠に納得する」資料。

**本スキルの方式は「テンプレート忠実再現(写経)」である。** 実在BCG資料12枚を
shape単位で採寸したブループリント(blueprints.md、R1〜R11+再掲オーバーレイ技法)が
実装の正であり、実装者は
レイアウトを**発明せず**、ブループリントの座標・寸法・色を写経してコンテンツ
スロットに中身を流し込む。品質は「センス」ではなく「写経の忠実さ+機械監査」で出す。

## 絶対原則(全Phaseで優先)

1. **1スライド=1メッセージ**。メッセージは「主張を含む完全な文」(体言止め禁止)
2. **ボディはメッセージの証明**。メッセージと無関係な要素は1つも置かない
3. **色は意味**。アクセント1色(緑)+状態色のみ。装飾目的の色追加は禁止
4. **数値は仕様**。色はhex、位置はcm、文字はptで指定・検証する。「だいたい」禁止
5. **自己申告不可**。「できました」ではなく監査ループ(audit-loop.md)の証拠で完了判定
6. **密度で語る**。BCG級=1枚で議論が完結する高密度の証拠パッケージ。本編の分析スライドは
   密度基準(density-composition.md §1)を満たすまで証拠を掘り増す。薄いスライドは未完成
7. **数値は描く**。数値3個以上の比較・構成・推移は必ず比例描画チャートにする。
   数字をテキストボックスに書いて並べただけの「チャート風」は差し戻し対象
8. **レイアウトを発明しない**。座標・寸法・色は blueprints.md の写経。文字が入らない
   ときは座標を動かすのではなく文字を削る(スロット上限は設計段階で守る)
9. **監査は実行**。audit-loop.md L2の監査スクリプトを実際に実行しPASSログを得るまで
   完成と言わない。ログなしの「確認しました」は虚偽報告

## 全体ワークフロー

```
Phase 0: 入力受領+ヒアリング(目的・読者・枚数感を1回にまとめて質問)
   ↓
Phase 1: メッセージ抽出とストーリーライン設計   → message-storyline.md
   ↓
Phase 2: スライド設計書の作成(全枚数ぶん)      → pattern-library.md で型を決定
   ↓     【ユーザー確認ポイント】設計書を提示し、実装前に承認を得る
Phase 3: 実装(python-pptx)                      → design-system.md の仕様値に準拠
   ↓
Phase 4: 3層監査ループ(構造→仕様→視覚、最大3周) → audit-loop.md
   ↓
Phase 5: 納品(pptx+スライド設計書+監査記録)
```

参照ファイルは6つ。**Phase 1の前にすべて読む**:
- `references/message-storyline.md` — 文章→メッセージ抽出→ストーリーライン→スライド分割、数字の見せ方
- `references/pattern-library.md` — 基準スライドR1〜R11の意味と使い分け、表現パターン19型、選択決定木
- `references/density-composition.md` — 情報密度の定量基準、視覚エンコーディング義務、複合構成C-1〜C-5、データ→切り口設計
- `references/blueprints.md` — **実装の正**。R1〜R11のshape単位設計図(座標・寸法・スロット上限)、再掲オーバーレイ、写経ルール
- `references/design-system.md` — 配色パレット(hex)、タイポグラフィ(pt)、共通部品、比例描画チャートの幾何式、python-pptx実装規約
- `references/audit-loop.md` — 3層監査、**実行必須の機械監査スクリプト仕様**、差し戻し基準、完成宣言の条件

## Phase 0: 入力受領+ヒアリング

- 入力は「分析文章」(Markdownレポート、evidence台帳、箇条書きメモ等)。文章がない
  口頭依頼のみの場合は、先に内容を文章化して確認してから本スキルに入る
- 不足情報を**1回にまとめて**質問する。最低限:
  **①資料の目的**(意思決定を取りに行く/報告/検討素材)、**②読者**(経営層/実務層/顧客)、
  **③枚数感・持ち時間**(5分なら5〜7枚、30分なら15〜25枚)、**④機密表記の要否**
- 読者が実行者本人(個人向け資産計画等)の場合は、経営層向けの「実務詳細を見せない」
  粒度基準を適用せず、実行に必要な実務数値(金利・利回り等)を本編に残してよい
- 既にテーマ特化スキル(shisan-keikaku-method、meigara-bunseki-method等)の報告書が
  ある場合はそれを正とし、スライド化で新しい主張を勝手に追加しない

**銘柄分析報告書(meigara-bunseki-method)を入力とする場合の変換規定**:
- 入力はWord報告書(またはそのMarkdown原稿)。**コンテンツの正は報告書、
  表現の仕方(パターン選択・密度・デザイン)の正は本スキル**という分担で変換する
- 報告書のAppendix C(図表F1〜F14→bcg表現パターン名の変換マップ)を出発点とし、
  **R番号・レイアウトの確定は本スキルの決定木(pattern-library.md)で行う**
  (報告書側のパターン名候補が決定木の結果と食い違う場合は決定木を優先し、
  相違理由を設計書に記す)
- 報告書の章構成(1章サマリ〜11章リスク・投資アクション)は目次トラッカーと
  1対1対応させる。evidence台帳(Appendix A)・計算前提(Appendix B)の数値は
  スライドの数値全打ちの供給源として使う
- 報告書の言語規律(日本語主体・英語引用は和訳併記)をスライドでも維持する

## Phase 1: メッセージ抽出とストーリーライン

message-storyline.md に従い、①文章から主張と根拠を抽出、②ピラミッド構造に整理、
③ストーリーライン(スライドの並び)を確定する。ここが品質の7割を決める。
入力が生データ(Excel・決算数値等)を含む場合は、抽出の前に
**density-composition.md §5 の標準切り口で複数の集計を作り**、メッセージ性の強い
切り口を選んでから主張を立てる(データを1つの見方でしか見ないまま書き始めない)。
**図を描き始める前に、全スライドのメッセージラインだけを並べて通し読みし、
それだけで話が通じることを確認する**(メッセージラインの通し読みテスト)。

## Phase 2: スライド設計書

スライド1枚ごとに以下を記した設計書を作る(フォーマットは message-storyline.md 末尾):

- メッセージライン(1文)/ リード文(任意)
- 表現パターン(pattern-library.md の決定木で選択。記載は4通り:
  ①P-1〜P-4/P-15〜P-19を選んだ場合は対応するR番号+選択理由、
  ②決定木が「R5型」「R6型」を直接出力した場合はその型名をそのまま+選択理由、
  ③P-5〜P-14の場合は「R対応なし・P-x準拠」+選択理由、
  ④再掲オーバーレイ使用時は「P-19+再掲オーバーレイ(ベース: Slide N)」)
- 複合構成(density-composition.md のC-1〜C-5から選択。なしの場合は理由)
- **スロット充填表**: 選んだRブループリント(blueprints.md)の全コンテンツスロット
  《》に対し、実際に入れる文字列・数値を**上限字数の検算付きで**列挙する
  (スロットが埋まらない=密度不足、溢れる=要約不足。ここで解消してから実装へ)
- 密度検算(density-composition.md §6: 想定文字量・情報単位数・数値個数・階層。
  薄すぎ警報に該当したら実装に進まない)

設計書をユーザーに提示し、**承認を得てから実装に進む**。ここで方向を直す方が
実装後の手戻りより圧倒的に安い。

## Phase 3: 実装(=ブループリントの写経)

- 各スライドは、設計書で選んだRブループリント(blueprints.md)の**shape表を上から
  順に写経**して実装する。python-pptxが使える環境ではpython-pptx、ローカルWindows等
  ではOffice COMでもよいが、いずれも座標・寸法・色・ptは表の値をリテラルで使う
- **スロット上限を超える文字は実装前に削る**。auto_size・自動縮小・座標の微調整で
  「収める」ことを禁止(表示崩れの根源)
- コンテンツがどのブループリントにも収まらない場合は、レイアウトをいじらず
  Phase 2に戻ってコンテンツを再構造化する(分割・要約・切り口変更)
- チャートはdesign-system.md §7の幾何式で「データ辞書→座標計算→描画」の順に実装する

## Phase 3.5: 機械監査の実行(実装と一体)

- audit-loop.md L2の監査スクリプト(bounds/palette/font/text-fit/overlap/blueprint/
  chart比例)を**実装・実行**し、違反0のPASSログを取得する
- 違反が出たら該当shapeを修正して再実行。**PASSログが出るまでPhase 4に進まない**

## Phase 4: 3層監査ループ

audit-loop.md に従い L1(構造)→L2(仕様=Phase 3.5のPASSログ確認)→L3(視覚) を通す。
- 指摘は Blocker / Major / Minor に分類し、Blocker/Major が0になるまで修正
- 最大3周。3周で解消しない項目は「既知の制約」として納品時に正直に報告する
- L3(視覚)はレンダリング画像を実際に目視する。**レンダリングせずに完成宣言する
  ことを禁止する**(レンダリング手段がない環境では、その旨と代替検証を報告)

## Phase 5: 納品

- 成果物: ①pptxファイル ②スライド設計書 ③L2機械監査のPASSログ ④監査記録(検出→修正の履歴)
- 出力先: claude.ai環境では `/mnt/user-data/outputs/`、ローカルではユーザー指定先
- 納品時に「未解消の既知の制約」「データの出所一覧」を必ず添える
- ユーザーからのフィードバックは audit-loop.md の差し戻しプロトコルで受け、
  該当スライドの設計書から修正する(pptxだけの場当たり修正をしない)
