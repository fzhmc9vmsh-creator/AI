# 投資資料の作り方の詳細(Phase 0〜6 の全文)

> 作業の順番と検査は SKILL.md(手順書)が正。ここは各工程で「読む」と指示された節だけを読む。
> 数字は台帳(facts_deck.json)から F() で引き、組み上がった資料は lint_deck.py で照合する(SKILL.md)。

戦略コンサルファーム(BCG水準)の構成品質でパワーポイントを作成するための手順書。
テーマは2系統: **①銘柄分析** / **②資産運用計画**。

## 全体ワークフロー(必ずこの順序で実行)

```
Phase 0: 用途確認(①か②かを必ずユーザーに質問)・入力確認
   ↓
Phase 1: 分析結果の受領・棚卸し(分析は前工程で完了済み。ここでは新規分析をしない)
   ↓
Phase 2: ストーリーライン設計
   ↓
★チェックポイント1: 構成案(目次+各スライドのメッセージ)をユーザーに提示し承認を得る
   ↓ (承認 → 次へ / 修正指示 → Phase 2に戻るループ)
Phase 3: スライド詳細設計(レイアウト・図表の割り当て)
   ↓
Phase 4: 実装(pptxスキルを併用)
   ↓
Phase 5: QAループ(画像レンダリング→検査→修正、最大2周)
   ↓
Phase 6: 納品(ファイル提示+構成サマリ)
```

**重要**: ユーザーは「候補を提示→承認→実装」のワークフローを強く好む。チェックポイント1を省略して
いきなりpptxを作り始めることは禁止。

## 第2版の必須事項(2026-10-17、利用者のフィードバックを反映。全 Phase で優先)

`references/deck-rules-v2.md` を必ず読む。要点:
1. **全スライドに見出し帯**: 左上に現在地(章 › 節(k/n))、右上に章の進捗、その下に「テーマ: …」の札と
   「なぜ見るか」の 1 行。章・節・テーマ・なぜ・タイトル・順番は `meta.js` で一括管理し、ページ番号は自動。
2. **事業理解は 3 枚**(事業の積み木 + 5W1H + 用語の注釈 / 事業どうしの関係図 / 注目度の高い成長分野)、
   **会社のシナリオは 2 枚**(ストーリー図 / 部品の採点と会社目標の信頼度)。
3. **関係図の基準**: レーンで領域を分け、自社を事業・資産に分けて 10〜14 箱、矢印に数量、①〜⑥ の仕組みを
   右パネルで説明、上がる条件・下がる条件、期間が論点なら時間軸。重なりは 0 件。
4. **情報の少ないスライドを作らない**(前提条件だけの条件は評価一覧に統合)。
5. **条件5 は経歴から評価**(meigara-bunseki-method の condition-guide 条件5)。
6. **改行**: タイトルは "\n" で意味の切れ目に改行。末行 1〜2 文字・数字と単位の泣き別れを作らない。
7. **Windows 向けはフォント Meiryo UI**(欧文・数字も同じでよい)。
8. **部品と監査**: `scripts/`(lib.js・meta.js・audit_deck.py・one.js・build.js・examples/s08b.js)を使う。
   1 枚ずつ `node one.js NN` で「図の重なり 0 件」と監査 PASS を確かめ、画像を目で見てから次へ進む。

## Phase 0: 用途確認・入力確認

### 用途の質問(必須・省略禁止)
作業開始前に、**必ず最初に「①銘柄分析と②資産運用計画のどちらのパワポを作成するか」を
ユーザーに質問する**。依頼文から自明に見えても確認する(両方の場合は2部構成にするか
別ファイルにするかも併せて確認)。回答を得てから該当の参照ファイルを読む:

| 回答 | 分岐 | 読むべき参照ファイル |
|---|---|---|
| ① | 銘柄分析 | `references/stock-analysis.md` |
| ② | 資産運用計画 | `references/asset-plan.md` |

どちらの分岐でも `references/design-spec.md`(デザイン規定)は**必読**。

### 前提: 分析は前工程で完了している
このスキルの役割は**「完了済みの分析結果をBCG級のスライドに落とし込むこと」**であり、
分析そのものではない。標準の入力は前工程の分析スキルが出力した**報告書**
(①=銘柄分析メソッド、②=資産運用計画メソッドの報告書。evidence台帳を内包)。
報告書がなく分析未実施の状態で依頼された場合は、先に該当の分析スキルでの
分析実施を提案する(パワポだけ先に作らない)。

### 必須入力のチェックリスト
受領した報告書/分析結果に以下が揃っているか棚卸しし、**不足分のみを1回の質問に
まとめて確認**する。勝手に推測・新規調査で埋めない。

**①銘柄分析**: 銘柄名/ティッカー、13条件それぞれのS〜F評価と根拠、各条件の「構造」の説明
(例: ORCLの「陳腐化しやすいGPUは顧客が前払い/持込み、自社は陳腐化しにくい建物・冷却・
電力に投資する」といった仕組みの記述)、**構造評価の導出ロジック(評価分布と適用ルール)、
構造的要因サマリー(押し上げ/押し下げ要因)、バリュエーションブロック(利益の質→
数字への波及マップ、市場の織り込みとカタリスト、将来5年EPS推移[過去成長率不使用]、
質→許容PEG、目標株価と乖離%、最終判断とトリガー)**、主要数値と出所。
※条件9は「AIにかかわる部品・サービスを扱う企業のみ適用」の軸。AI非関連企業の台帳では
条件9が対象外(N/A)となっているはずで、その場合も通常どおり資料化する
(条件9スライドはN/A表示、評価一覧・分析ロジックはカウント除外を明示)。
**②資産運用計画**: 資産運用計画メソッドの報告書(evidence台帳②)。具体的には:
ゴール定義(**ユーザー設定年齢での目標純資産**)、前提条件一覧(Excel由来値と修正後値)、
収入前提・支出前提、借入条件(増額可否・担保/追証条件含む)、現在→将来の資本構成推移、
施策一覧(6レバー別インパクト・実行時期・To Do・注意点、副業/独立提言がある場合は
習得スキル計画と顧客想定、投資的支出は投下額・回収期間・撤退基準)、シナリオ(ベースライン/施策後/ストレス)、
フェーズ別スケジュール、KPI定義、外部環境の要点と出所。

## Phase 1: 分析結果の受領・棚卸し

- **新規の分析・調査は行わない**。受領済みの分析結果を、スライド化できる粒度に整理する。
- ①の場合: 「条件番号 × 評価(S〜F) × 根拠一文 × 構造の説明 × 数値 × 出所」の一覧表
  (evidence台帳)を作る。構造の説明が言葉だけの条件は、Phase 3で図解できるよう
  「登場アクター/カネ・モノ・リスクの流れ」に分解しておく。
- ②の場合: 「前提条件一覧」(収入・支出・借入条件・利回り・税率)と「提言・スケジュール」を
  受領内容から確定する。
- スライドに載せる**すべての定量データに出所を記録**する。出所のない数値は載せない。
  これはコンサル資料の生命線。分析結果に出所が欠けている数値があれば、Phase 0の
  不足確認の質問に含める。
- 例外: 株価など「資料作成日時点の値」への更新をユーザーが明示的に求めた場合のみ
  Web検索で取得してよい(その場合も出所と取得日を記録)。

## Phase 2: ストーリーライン設計

### 原則(ピラミッド構造)
1. **最終結論を先に決める**(①: 合格/条件付き合格/不合格、②: 推奨プラン)。
2. 結論を支える3〜5本の柱(キーメッセージ)を決める。
3. 各柱を1〜3枚のスライドに割り当てる。**1スライド=1メッセージ**。
4. すべてのスライドタイトルは「メッセージ型(主張を含む完全文)」で書く。
   - 悪い例: 「財務分析」
   - 良い例: 「クラウドIaaSのRPOが3年でx倍に拡大し、従量課金型収益の比重が急速に上昇」

### 標準デッキ骨格(BCGサンプル準拠)
```
1. 表紙
2. エグゼクティブサマリ(結論と柱を1枚で)
3. アジェンダ(トラッカー型: 章ごとに再掲し、現在章をハイライト)
4〜n. 本編(章ごとに中扉→コンテンツスライド)
n+1. サマリと示唆(左: 事実サマリ / 右: 示唆・ネクストアクション)
n+2. Appendix(詳細データ、計算前提)
最終. クロージング
```
枚数の原則:
- ①: **13条件それぞれに1枚ずつ**の深掘りスライド(構造図)+評価総括に加え、
  **バリュエーションと最終判断の章(波及マップ/カタリスト/5年EPS/目標株価算出/
  2軸マトリクス)がクライマックス**。全体で28〜33枚。
- ②: 主要テーマ(収入前提/支出前提/借入条件/資本構成比較/提言/スケジュール)は
  **各1枚で完結**させる(そのスライドだけ見れば結論と根拠がわかる密度)。全体で12〜16枚。

### ★チェックポイント1(承認ゲート)
以下のフォーマットでユーザーに提示し、承認を待つ:
```
【構成案】全n枚
#1 表紙: (タイトル案)
#2 エグゼクティブサマリ: (結論の一文)
#3 アジェンダ
#4 (メッセージ型タイトル) — 使用レイアウト: 評価マトリクス
#5 (メッセージ型タイトル) — 使用レイアウト: チャート+テイクアウェイ
...
```
修正指示があれば構成を直して再提示(ループ)。承認が出るまでPhase 3に進まない。

## Phase 3: スライド詳細設計

各スライドについて `references/design-spec.md` の**スライドタイプライブラリ**から
レイアウトを選び、以下を確定する:
- タイトル(メッセージ型)+ キッカー(タイトル下の小さな説明行、例:「各国政府のAIへの取組」)
- 本文要素(図表の種類、行列の中身、コールアウト文言)
- フッター(出所、ページ番号)

### 図表選択の分岐
| 伝えたいこと | 使う図表 |
|---|---|
| 合否・充足度の一覧 | 評価マトリクス(○△×表) |
| 大小・成長の比較 | 縦棒/横棒チャート+差分コールアウト |
| 時系列の推移・将来予測 | 折れ線 or 縦棒(実績は濃色、予測は薄色/斜線) |
| 構成の内訳 | 積み上げ棒(円グラフは原則使わない) |
| 資産の増減要因 | ウォーターフォール |
| 分類・パターン | A/B/C行フレームワーク表 |
| 計画の時間軸 | ロードマップ(フェーズ矢羽+マイルストーン) |
| トレードオフ・ポジション | 2軸マトリクス |

同じレイアウトを3枚以上連続させない。表が2枚続いたら次はチャートにする等、視覚的リズムを作る。

## Phase 4: 実装

1. **必ず** `/mnt/skills/public/pptx/SKILL.md` と `pptxgenjs.md` を読んでから実装する。
2. `references/design-spec.md` のカラーパレット・タイポグラフィ・マスターレイアウト規定に従う。
3. 16:9、全スライドで余白・フォント・色を統一。フッター(出所/©表記/ページ番号)を全コンテンツ
   スライドに入れる。
4. チャートはpptxgenjsのネイティブチャート機能またはシェイプで描画する(画像貼り付けの粗い
   チャートにしない)。

## Phase 5: QAループ

pptxスキルの手順でスライドを画像化し、以下を検査する。**最大2周**で収束させる。

### QAチェックリスト
- [ ] 全タイトルがメッセージ型か(体言止めの「〜分析」「〜について」が残っていないか)
- [ ] 1スライド1メッセージが守られているか
- [ ] テキストのはみ出し・重なりがないか(最頻出の欠陥。最優先で確認)
- [ ] すべての定量スライドに出所があるか
- [ ] 数値の整合性(エグゼクティブサマリの数値と本編の数値が一致するか)
- [ ] アジェンダトラッカーのハイライト位置が章と一致しているか
- [ ] ページ番号が連番か
- [ ] 色・フォントが design-spec と一致しているか
- [ ] ①の場合: 全13条件に1枚ずつスライドがあり、各枚に構造図とS〜F評価バッジがあるか
- [ ] ①の場合: 目次(トラッカー型)・分析ロジック(T16)・構造的要因サマリー(T17)・
      目標株価算出(T18)・最終判断マトリクスが揃っているか
- [ ] ②の場合: 主要テーマの各スライドが単体で完結しているか(他スライドを見ないと
      理解できない前提の抜けがないか)
- [ ] 投資助言ではない旨の免責注記が表紙裏またはAppendixにあるか

問題を修正したら該当スライドのみ再レンダリングして確認。

## Phase 6: 納品

1. 完成した .pptx を `/mnt/user-data/outputs/` に置き、present_files で提示する。
2. 併せて以下を短く報告する: 総枚数、結論(①なら判定結果、②なら推奨プラン)、
   ユーザーが差し替えたくなりそうな前提数値の一覧(次回更新を容易にするため)。
3. 「数値の更新」「章の追加」等の再依頼時は、既存pptxを編集する(ゼロから作り直さない)。
