## 1. 見出し帯(全スライド必須)

利用者の指摘: 「左上に資料の階層、現在地が無い」「全スライドに、何故それを説明してるかを示すテーマを見出しにして。今のままだとなぜその説明や解説があるか分からない」

| 位置 | 中身 | 書式 |
|---|---|---|
| 上端の灰帯 左(y 0.06) | 現在地: `第2章 事業・需給・成長 › 2-1 事業理解(1/3)` | 9pt。節名は濃緑の太字。同じ節が複数枚なら (k/n) |
| 上端の灰帯 右 | 章の進捗: 章ごとの札(`1 総括` `2 事業・需給` …)。今の章だけ緑で塗る | 8pt |
| 2 段目(y 0.42) | テーマの札 `テーマ: 事業理解` + `なぜ見るか  …` | 10pt。札は濃緑の塗りに白字 |
| 3 段目(y 0.76) | タイトル(メッセージ型の完全文) | 19pt 太字、2 行まで、改行位置は "\n" で明示 |
| 4 段目(y 1.41) | リード(何をどう読むか) | 9.5pt 灰、1 行 |

- **テーマ**は「このスライドが資料全体の中で担う論点」。語彙の例: 結論 / 評価の全体像 / 事業理解 / 成長分野 / 会社のシナリオ / 収益構造 / 競争優位 / 需給 / 成長の前提 / 資金と信用 / 条件ごとの論点名(例: 競争優位の持続(条件1))/ 市場との差分 / 価値評価 / 最終判断 / リスク / 投資行動 / まとめ / 前提と履歴。
- **なぜ見るか**は 1 行(全角 60 字以内)で、「何を判断するための材料か」を書く。例: `事業どうしが顧客と資金をどう受け渡すかを見る。単体の売上より、つながりが成長を生むため`。
- **一括管理**: 章・節・テーマ・なぜ・タイトル・順番は `meta.js` に集める。ページ番号は順番から自動で振る。スライドのファイルにはタイトルとページ番号を書かない。
- **中扉**: 章の「なぜ」と「この章の構成(節とページ範囲)」を出す。前提条件のように単独スライドにしない項目は、中扉に注記する。

## 2. 構成(銘柄分析の資料)

1. **事業理解は 3 枚**(利用者: 「事業理解の根源。もう 2 枚増やして」)
   1. 事業の積み木(層 × 動く場所)+ 製品群の 5W1H 台帳 + **用語の注釈**(資料に出てくる新しい用語を出てくる順に 1 行で説明。10〜12 語)
   2. **事業どうしの関係図**: 顧客 → 事業(稼ぐ柱 → 伸びる柱)→ 提携先・資本の出し手。顧客・技術・現金の受け渡しを数量つきで描く
   3. **分析的に注目度の高い成長分野**: 分野ごとの規模・伸び・1 株価値への効き・確度・見るべき KPI・注目度(★)と、2 軸の位置。利用者が例に挙げた分野(ORCL なら Database@)は必ず入れる
2. **会社のシナリオは 2 枚**(利用者: 「会社の持つシナリオ、ストーリーの図がない」)
   1. **ストーリー図**: 会社の目標(数値と年)→ 需要 → 資金 → 建設・投資 → 収益化 → 成果。上積みの部品、赤の制約、循環(稼いだ現金が次の投資へ)、目標年までの時間軸と節目
   2. 部品の採点(作動しているか、規模で加重)と、会社目標・コンセンサス・自前の推計の差(会社目標をどこまで信じるか)
3. **情報の少ないスライドを作らない**(利用者: 「20 ページとかホントにいる？総括で良くない？」)。前提条件(上場市場など)だけの条件、タイル 3 枚だけのスライドは、評価一覧や総括に統合する。
4. **条件5(経営者)は経歴から評価する**(利用者: 「CEO は経歴からその事業への経験等に鑑み経営能力を図る」)。meigara-bunseki-method の condition-guide 条件5 の手順で経歴台帳を作り、スライドは「経歴 → 現職 → 担う事業 → 結果」の関係図にする。

5. **成長企業は「成長の尺度」の章を立てる**(利用者: 「成長企業を見る尺度として構造評価が足りない」、2026-10-18)。meigara-bunseki-method の growth-stage-evaluation.md に従い、次の 3〜4 枚を 13 条件の前に置く。
   - **成長エンジン(G1〜G8 の採点)**: 獲得 → 主口座化 → クロスセル → 製品当たり CAC の低下 → さらに獲得、の連鎖を数量つきの関係図で示し、G1〜G8 の判定と 13 条件への効きを並べる。
   - **獲得投資の裁量性**: 純増会員・純増製品当たりの販促費の時系列と、6 つの検査(限界 CAC・解約・価格・競合・経営の運用・有機的獲得)の判定表。成長投資控除前 EPS と、EPS の成長の分解を並べる。
   - **段階の判定**(必要なとき): B2B 基盤の段階(失注 → 底打ち → 自社利用 → 再成長)、資本構造の転換(自己資本の自給率)、新技術のコスト効果。
   - **業態の組み合わせと資本コスト**(組み合わせが優位の源泉のとき、例: 銀行免許 × フィンテック): 希少さの表(片方だけを持つ相手と比べる)、再現コストと部品ごとの再現例、貸出 100 ドル当たりの必要利回りを負債と株主資本に分けた比較、調達の優位の年額と販促費・開発費の比較。
   - **シナリオ確率の節点ツリー**(価値評価の章): 強気(うまくいった場合)の中身と 1 株当たり価値、節点ごとの確率と根拠、市場の暗黙の確率との比較。

6. **成長企業の初歩のスライド(第5版、利用者: 「全部初歩中の初歩」)**: 次を必ず入れる。
   - **フェーズと二層の構造**: 会社全体と事業ごとのフェーズ、13 条件の「現在 × 将来 × 実現確率 × 統合」の表。
   - **フライホイールとバリューチェーン**: 会員(顧客)を中心にした体験の束と、お金の流れを分けて描く。体験の要素を競合と比べた表。
   - **根幹 KPI の率**: 前期比・前年比・率の推移・純増の前年比を並べる(絶対数の純増だけで減速と書かない)。
   - **EPS の四半期分解**: 収益・税引前利益・税率・株数・EPS の表と、EPS の前年比を要因別に積み上げた図。
   - **マクロの両面**: 経路ごとの効果(+/−)の滝グラフと、市場の織り込みとの比較。
   - **資本モデルの業界比較**: 保有と売却の比率を同業と並べ、利点と欠点の表。
   - **条件6 の市場比較**: 対象・市場・同業の PER・成長率・PEG の表または散布図。
   - **構造評価 → 許容 PEG の導出(第5.1版)**: 条件の構成 → 平均点 → 等級 → 帯の中の位置 → 許容 PEG・α の流れ図。前の版を同じ規則で計算し直した値を並べる。
   - **年度別理論株価(第5.2版)**: 妥当 PER = 許容 PEG × 当該年度から 3 年の成長率の年度別テーブル(他の方法と平均しない)。
     「PEG 1.0 固定」の値を必ず併記し、DCF・TBV×ROTCE・同業の PER は交差確認として差の理由と並べる。
   - **信用と資本の制約(第5.2版)**: 純償却率と資本比率の同業比較の表、損失率・増資を動かした理論株価、株価が示す損失率の逆算。

## 3. 関係図の基準(条件スライド・事業の関係・会社の筋書き)

**図の形はその企業の事業の形に合わせる(第5版)。** 会員型・プラットフォーム型は会員を中心にした放射(ハブ)とお金の流れの帯に分ける。連鎖が芯なら循環(フライホイール)。資金・モノが流れるなら左→右の流れ図。主体が分かれるときだけレーン。線の交差が出たら、形が事業に合っていない兆候として形を変える(SOFI 第2版の 9 ページ目で、会員型の事業をレーンに詰めて線が交差した失敗から)。

利用者の指摘: 「関係図がお粗末すぎる。図の配置、粒度、深さ全部足りない」「図のクオリティが低い」

| 観点 | 基準 | 旧版の失敗 |
|---|---|---|
| 配置 | レーン(背景の帯)で「誰の領域か」を分ける。左から右へ、お金・モノの流れの順。同じ行の箱は直線、行をまたぐ線は通路で直角に折る | 5 つの箱を格子に散らし、斜めの線で結んだ |
| 粒度 | 自社を 1 つの箱にしない。条件に関わる事業・資産・機能に分ける(3〜5 箱)。外部も 3〜5 箱。合計 10〜14 箱 | 「Oracle」1 箱 + 外部 4 箱 |
| 深さ | 矢印と箱の副題に数量(金額・率・期間)。仕組みを ①〜⑥ の番号で線に付け、右パネルに「何が起き、なぜ評価に効くか」を 1 項目 2 行で書く。リスクの所在(誰が負うか)を赤枠・札で示す | 線のラベルが「保守料」だけ、根拠は別の箇条書き |
| 評価の境界 | 右パネルの下に「上がる条件」「下がる条件」。評価 C 以下は監視 KPI の帯 | 評価の理由だけ |
| 時間 | 期間が論点(優位の期間、契約・リース・償却の長さ)なら時間軸の帯を図の下に入れる | なし |
| 読みやすさ | 線のラベルは全角 10 字前後。入らない線は番号の丸だけにして右で説明。ラベル×箱・ラベル×ラベル・線×無関係の箱の重なりは 0 件(flowMap が自動で検出) | ラベルが線や箱に重なった |

部品: `L.flowMap`(レーン・囲み・箱・直角の線・番号・重なり検出)、`L.mechPanel`(仕組み・理由・上がる/下がる条件)、`L.kpiBand`、`L.timeBand`。

## 4. 改行と文字

利用者の指摘: 「改行の位置が悪い」

- タイトルは意味の切れ目で "\n" を入れる。各行は 19pt で 11.13in に収まる長さ(全角 38 字相当)まで。監査で折り返しが出たら Major。
- 本文・箱の副題は、末行が 1〜2 文字にならないように "\n" を入れるか語を削る。数字と単位を別の行に分けない(`2,880 億` / `ドル` のような泣き別れ)。
- 監査(`audit_deck.py`): title-wrap(Major)、orphan(テイクアウェイ・リード・なぜの行は Major、他は Minor)、num-split(Minor)。Minor も画像で実際に起きていれば直す。
- 描画の確認は LibreOffice(代替フォント)。Windows の Meiryo UI と幅が違うので、見積もりに 8% の余裕を持たせてある。

## 4b. 実装の注意(pptxgenjs 3.12 で実際に起きたこと)

- **保存は必ず `L.save(pres, file)`**(`pres.writeFile` を使わない)。pptxgenjs は複数の文字の塊(runs)を持つ段落で `<a:pPr>` を塊ごとに出し、スキーマ違反になる(Windows の PowerPoint で修復の警告の原因)。`save` が段落ごとに最初の 1 つだけを残す。付属の validate.py ではこの違反を検出できない。
- **同じ項目の中の改行**は "\n" で書く。`L.bullets`・`L.mechPanel` は `softBreakBefore`(`<a:br/>`)に変換する。pptxgenjs は `bullet` を持つ塊で段落を分けるので、続きの塊に bullet を付けてはいけない。
- **右パネル(mechPanel)**は文字量から高さを見積もり、11〜9pt のうち収まる最大の大きさを選ぶ。理由の箱は中身に合わせ、上がる/下がる条件は下端に揃う。
- **凡例**は図で使った線の種類だけを出す。
- **監査の幅の見積もり**は描画の代替フォントより 8% 厳しい。部品(箱の名前・線のラベル)も同じ余裕で折り返しを決める。

## 5. 制作の分担と手順

| 担当 | 仕事 |
|---|---|
| Opus(指示) | 構成と meta.js、各スライドの指示書(関係図は箱・矢印・仕組み・理由・境界の中身まで)、関係図の手本 1 枚、最後の目視確認 |
| Sonnet | 関係図、複合構成、新しい型のスライド |
| Haiku | 座標と文字が決まった表・チャート、機械的な修正 |

1. `scripts/` を作業フォルダに写し、`npm i pptxgenjs@3.12.0`(python-pptx も必要)。`meta.js` を案件に合わせて書き換える。
2. 1 枚ずつ `node one.js 17` → 図の重なり 0 件・監査 PASS・画像を目で見る。
3. `node build.js` → 全体の監査 `python3 audit_deck.py ORCL_deck.pptx` → 全ページを画像にして目視。
4. 指示書と meta.js、監査ログを納品物と一緒に残す。
